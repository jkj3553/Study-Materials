Question 1. a)

Differentiate between Waterfall model and Spiral model. [Marks Allocated in Paper]

Parameter of Comparison Waterfall Model Spiral Model
Basic Structure A linear sequential process model where each phase (Requirements, Design, Implementation, Testing) cascades downward strictly one after the other. An iterative, risk-driven process model represented as a spiral, where each loop in the spiral represents a phase of the software process.
Risk Management Lacks explicit risk assessment mechanisms. Risks are usually discovered late during the testing or deployment phases. Explicit risk assessment and risk resolution are core activities built directly into every single iteration of the spiral.
Requirements Flexibility Highly rigid. Requirements must be completely frozen before design begins. Very poor at accommodating changing customer requirements. Highly flexible. Requirements can evolve dynamically as the project loops through new spirals and prototypes are evaluated.
Target Application Best suited for well-understood, stable projects (e.g., hardware-interfacing systems, embedded control) where specifications are clear upfront. Best suited for large-scale, complex, and highly innovative projects where technical and business risks are high.

Question 2.

The ACM and the IEEE have cooperated to produce a joint code of ethics and professional practice. Discuss the principles that software engineers must adhere to protect the welfare of the society. [Marks Allocated in Paper]

Software engineers have ethical responsibilities that extend beyond basic technical coding. The ACM/IEEE-CS Joint Task Force defines 8 core principles that engineers must uphold to protect society:

  1. PUBLIC: Software engineers shall act consistently with the public interest. They must prioritize public safety and welfare over commercial success.
  2. CLIENT AND EMPLOYER: Software engineers shall act in a manner that is in the best interests of their client and employer, provided it is completely consistent with the public interest.
  3. PRODUCT: Software engineers shall ensure that their products and related modifications meet the highest professional standards possible.
  4. JUDGMENT: Software engineers shall maintain strict integrity and independence in their professional judgment.
  5. MANAGEMENT: Software engineering managers and leaders shall subscribe to and promote an ethical approach to the management of software development and maintenance.
  6. PROFESSION: Software engineers shall advance the integrity and reputation of the profession consistent with the public interest.
  7. COLLEAGUES: Software engineers shall be fair to and supportive of their colleagues.
  8. SELF: Software engineers shall participate in lifelong learning regarding the practice of their profession and promote an ethical approach to their practice.

Question 8. a)

All requirements are expressed as scenarios. The clients want the design to be simple and the software development to be planned and released in smaller portions. Identify the most suitable software development method to be adopted for the above requirements. Discuss the various practices involved in this method. [8 Marks]

1. Identification of the Method

The most suitable software development method for this scenario is Extreme Programming (XP), which is a highly prominent framework under Agile Software Development. The scenario explicitly mentions requirements written as "scenarios" (User Stories), a demand for "simple design," and software released in "smaller portions" (incremental delivery)—all of which are fundamental signatures of XP.

2. Key Practices Involved in Extreme Programming (XP)

  • Requirements as User Stories: User requirements are expressed directly as scenarios or "user stories" written on story cards, allowing the development team to break them down into implementation tasks.
  • Small, Frequent Releases: The software is built and delivered in small, iterative portions, allowing the client to see working software quickly and adjust requirements accordingly.
  • Test-First Development (Test-Driven Development): Executable test harnesses are written before the actual software code is written. The code is then developed specifically to pass those tests.
  • Continuous Refactoring: The engineering team maintains system simplicity through constant code refactoring, actively cleaning up the architecture to ensure it does not degrade as new features are added.
  • Pair Programming: Developers work in pairs at a single workstation. This provides continuous, real-time code inspection, shares knowledge, and improves overall code quality.
  • Customer Involvement: The client or end-user is actively involved in the development process, evaluating the smaller increments and validating the tests.

Question 8. b)

Discuss the advantages of software inspections over software testing. Identify the different roles and responsibilities in the inspection process. [6 Marks]

1. Advantages of Software Inspections over Dynamic Testing

Software inspections (static verification) involve reviewing source code manually before compilation. This provides distinct advantages over traditional execution testing:

  • No Defect Masking: During dynamic execution testing, one error can crash the program or corrupt data, masking other downstream bugs. In an inspection, the code is read statically, allowing the team to discover multiple independent defects in a single session without dealing with program crashes.
  • Catches Non-Functional Flaws: Inspections can catch issues that tests cannot physically execute, such as poor coding style, inefficient algorithms, bad naming conventions, or unmaintainable architectural structures.
  • Cost Efficiency: Finding and fixing a bug during an inspection is significantly cheaper and faster than discovering it during testing, which requires writing reproduction scripts, running debuggers, and recompiling builds.

2. Roles and Responsibilities in the Inspection Process

According to standard verification protocols, a formal inspection involves the following team roles:

  1. Author/Programmer: The individual who wrote the code. They are responsible for explaining the logic to the team and implementing the fixes for any defects found.
  2. Inspector (Reviewer): A technical peer who reads the code specifically to find bugs, logical errors, and non-compliance with organizational standards.
  3. Reader: The individual who reads the code aloud to the inspection team, walking them through the execution flow step-by-step.
  4. Moderator (Chairman): The leader who manages the inspection process, schedules the meetings, keeps the team focused on finding defects (rather than fixing them during the meeting), and ensures formal quality reports are logged.

Question 7. a)

Differentiate between structural testing and functional testing. [6 Marks]

Aspect of Comparison Structural Testing (White-Box Testing) Functional Testing (Black-Box Testing)
Testing Basis Test cases are designed based on deep knowledge of the internal source code structure and logic. Test cases are derived strictly from the external software requirements and functional specifications.
Primary Objective To exercise and validate internal logical execution paths, loop boundaries, and conditional branch statements (e.g., if-else blocks). To validate that the system accepts inputs and generates the correct outputs in accordance with business rules.
System Visibility The tester has full access to the source code (Clear/Glass box approach). The tester treats the software as a completely opaque "black box" with zero visibility into internal algorithms.
Common Techniques Path testing, statement coverage analysis, data-flow testing, and cyclomatic complexity graphs. Equivalence partitioning, boundary value analysis, and use-case scenario validation.

Question 7. c)

Assume that an organization has 10 legacy systems. The organization is planning the budget for the upcoming financial quarter and wants to discard some of the legacy systems so that new systems can be incorporated. Discuss the different clusters that need to be analyzed by the organization for discarding the legacy systems. [6 Marks]

When assessing legacy systems for budgeting and phase-outs, an organization analyzes the software across two dimensions: System Quality (technical health) and Business Value (operational importance). This evaluation creates four distinct clusters that dictate the system's fate:

  1. Cluster 1: Low Business Value & Low System Quality (The Discard Cluster)
  2. Analysis: These legacy systems suffer from severe technical debt, unmaintainable code, and constant failure, while simultaneously providing almost zero modern value to the core business operations.

  3. Action: Scrap completely. These systems should be the primary targets for discarding to free up budget space.

  4. Cluster 2: Low Business Value & High System Quality (The Archive Cluster)

  5. Analysis: The software is technically sound and runs well, but the business processes it supports have become obsolete or irrelevant to the company's current strategic goals.

  6. Action: Replace or phase out. The organization should stop active development and migrate any residual required tasks to COTS (Commercial Off-The-Shelf) tools.

  7. Cluster 3: High Business Value & Low System Quality (The Re-Engineering Cluster)

  8. Analysis: These are critical systems keeping the company running, but they are technically degraded, poorly documented, and expensive to keep online.

  9. Action: Re-engineer or Modernize. They cannot be discarded because of their business value. The budget must be allocated to clean up the architecture or replace them with a modern enterprise solution.

  10. Cluster 4: High Business Value & High System Quality (The Maintain Cluster)

  11. Analysis: Highly important, stable systems running smoothly.
  12. Action: Maintain. Keep them running with normal operational funding.

Question 7. b)

Discuss the set of laws proposed by Lehman with respect to program evolution. [8 Marks]

Exam-Perfect Answer:

Lehman and Belady studied the evolution of large-scale software systems and proposed a set of empirical laws—known as Lehman’s Laws of Software Evolution—that govern how "E-type" (embedded in a real-world environment) systems behave as they change over time.

To secure full marks, the key laws and their justifications must be defined:

  1. Law of Continuing Change:
  2. Statement: A program that is used in a real-world environment must continually change, or else it will become progressively less useful in that environment.

  3. Implication: Software is never truly "finished." Operating environments, business rules, and user expectations change, forcing the software to adapt or face obsolescence.

  4. Law of Increasing Complexity:

  5. Statement: As an evolving program changes, its structural complexity increases unless active work is done to maintain or reduce it.

  6. Implication: Without continuous refactoring and architectural cleanups, adding new features ad-hoc will degrade the code structure, leading to tight coupling and higher maintenance costs.

  7. Law of Large Program Evolution:

  8. Statement: Program evolution is a self-regulating process. System attributes such as size, time between releases, and the number of reported errors are approximately invariant for each system release.

  9. Law of Organizational Stability:

  10. Statement: Over a program's lifetime, its rate of development is approximately constant and independent of the resources devoted to system development.

  11. Implication: Adding more programmers to a legacy project does not proportionally speed up development due to the communication overhead and structural limits of the software.

  12. Law of Conservation of Familiarity:

  13. Statement: Over the lifetime of a system, the incremental change in each release is approximately constant.

  14. Implication: If a release tries to introduce too many changes at once, the system becomes highly unstable because developers lose familiarity with the core structure.

  15. Law of Continuing Growth:

  16. Statement: The functional capability of software systems must continually increase to maintain user satisfaction over their lifetime.

  17. Law of Declining Quality:

  18. Statement: The quality of software systems will appear to be declining unless they are strictly modified to reflect changes in their operational environment.

Question 8. c)

Path testing is a structural testing strategy whose objective is to exercise every independent execution path through a component or program. For a binary search program, design a path flow graph, where each node represents a line of code. Identify the number of independent paths to be tested using cyclomatic complexity and justify. [6 Marks]

Exam-Perfect Answer (Algorithmic Approach):

1. Baseline Algorithm for Binary Search

Instead of programming syntax, we define the logic using standard algorithmic steps. Each numbered step will correspond to a node in the flow graph.

  1. Start (Initialize Low and High boundaries)
  2. While (Low <= High) do:
  3. Calculate Midpoint
  4. If (Array[Midpoint] == Target) then:
  5. Return Found (Exit)
  6. Else If (Array[Midpoint] < Target) then:
  7. Set Low = Midpoint + 1 (Search Right Half)
  8. Else:
  9. Set High = Midpoint - 1 (Search Left Half)
  10. Return Not Found (Exit)
2. Control Flow Graph (CFG) Design

3. Cyclomatic Complexity Calculation

Cyclomatic Complexity (V(G)) defines the logical complexity of the algorithm and dictates the exact number of independent paths that must be tested to achieve 100% branch coverage.

It can be calculated using two standard formulas:

  • Method 1: Predicate Nodes Formula
  • V(G) = P + 1 (where P is the number of predicate/decision nodes)
  • Predicate nodes in this algorithm:
  • Node 2: While loop condition
  • Node 4: If match condition

  • Node 6: Else If greater/lesser condition

  • P = 3 => V(G) = 3 + 1 = 4

  • Method 2: Edge-Node Formula

  • Conceptually tying the two exit points (Node 5 and Node 10) to a single logical "End" point yields 12 Edges (E) and 10 Nodes (N).
  • V(G) = E - N + 2 = 12 - 10 + 2 = 4
4. Justification of the 4 Independent Paths

Because V(G) = 4, the testing strategy must explicitly execute the following 4 independent paths to ensure every logical condition is tested at least once:

  • Path 1 (Target Not in Array - Loop Bypassed): 1 -> 2 -> 10
    (Justification: The array is empty or the boundaries cross immediately, so the loop evaluates to False on the very first check).
  • Path 2 (Target Found Immediately): 1 -> 2 -> 3 -> 4 -> 5
    (Justification: The search target matches the exact midpoint on the first calculation).
  • Path 3 (Target is in Right Half): 1 -> 2 -> 3 -> 4 -> 6 -> 7 -> 2...
    (Justification: The target is greater than the midpoint, forcing the algorithm to update the lower boundary).
  • Path 4 (Target is in Left Half): 1 -> 2 -> 3 -> 4 -> 6 -> 8/9 -> 2...
    (Justification: The target is less than the midpoint, forcing the algorithm to update the upper boundary).
