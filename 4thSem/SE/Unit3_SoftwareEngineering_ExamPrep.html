Section 1 — Imp Questions

Imp QuestionCh 11 — Architectural Design
"Giving reasons for your answer, suggest an appropriate structural model and control model for the given systems and explain with diagrams."

This question always has two parts hiding inside it: pick a structural model (how the system is organised / how sub-systems share data) and pick a control model (who is in charge of starting/stopping things). Learn the options once, then you can answer this for any system they throw at you — just plug in the reasoning.

A. Structural models (system organisation styles)

These describe how sub-systems talk to each other and share data. There are three standard ones:

1. Repository model

All sub-systems share one central database/repository. A sub-system doesn't talk to another sub-system directly — it just reads/writes the shared repository.

Code generator

Design translator
Central Repository

Design analyser
Report generator
Example: CASE toolset architecture

Good when: large amounts of data must be shared, and sub-systems don't need to know how the data was produced (e.g. compilers, CASE tools, big data-processing systems).
Advantages: efficient sharing of large data; centralised management (backup/security); the shared schema is published once.
Disadvantages: all sub-systems must agree on one data model (a compromise); hard to evolve the schema; hard to distribute across machines; no room for sub-system-specific data policies.

2. Client-server model

A set of stand-alone servers, each offering a specific service, and clients that call those services over a network.

Client 1
Client 2
Client 3
↕ network ↕
Server A
Server B

Good when: the system is naturally distributed and each service has its own data (e.g. a film/picture library with separate video, picture, catalogue servers).
Advantages: data distribution is simple; makes good use of networked/cheaper hardware; easy to add/upgrade servers.
Disadvantages: no shared data model, so different servers may organise data differently — data exchange can be inefficient; each server repeats its own management logic; no central directory of what services exist.

3. Abstract machine / layered model

The system is organised into layers, each layer offering services only to the layer directly above it. If one layer's interface changes, only the neighbouring layer is affected.

Object management layer
Database system layer
Operating system layer

Good when: security matters (put critical assets in inner layers) or the system needs to be built/extended incrementally.
Disadvantage: can feel artificial — not every system naturally splits into clean layers.

B. Control models

These decide who controls the starting/stopping/sequencing of sub-systems.

1. Centralised control

  • Call-return (top-down subroutine) model: control starts at the top of a routine hierarchy (main program) and moves down through subroutine calls. Only suitable for sequential systems.
  • Manager model: one component (the manager) decides when to start/stop/coordinate other processes. Works for concurrent systems; in a sequential system it can be coded as a big case statement.

2. Event-driven control

  • Broadcast model: an event is announced to all sub-systems; whichever sub-system has registered interest handles it. Good for integrating sub-systems spread over a network.
  • Interrupt-driven model: used in real-time systems where a fast reaction is essential. Each interrupt type has a dedicated handler picked from an interrupt vector.

Imp QuestionCh 14 — Object-Oriented Design
"Identify the objects and develop an Object-Oriented Design (with UML class diagram showing generalization and aggregation) for a given system."

Step 1 — The OOD process (so you can structure your answer)

  1. Understand the context and how the system will be used (use-cases).
  2. Design the overall system architecture (layered/repository/etc, from Q1 above).
  3. Identify the principal objects.
  4. Develop design models (class diagram, sequence diagram, state diagram).
  5. Specify object interfaces.

Step 2 — How to actually find the objects

There's no single formula, but four standard approaches are used (write these even if the question doesn't explicitly ask for approaches):

ApproachIdea
Grammatical (linguistic)Underline nouns in the system description → candidate objects; underline verbs → candidate operations.
Tangible thingsLook for physical/real-world things in the domain (sensors, devices, people, documents).
BehaviouralLook at what behaviour the system needs, then decide which entity is responsible for each behaviour.
Scenario-basedWalk through a use-case scenario step by step; each noun/verb that shows up becomes an object/method.

In an exam, just skim the given paragraph, underline the nouns (they become classes), and underline the verbs attached to each noun (they become that class's operations).

Step 3 — Generalization (an "is-a" relationship)

When several classes share common attributes/operations, pull the common part into a super-class; the specific classes become sub-classes and inherit everything from the super-class, adding their own extra bits.

Employee (name, address, salary…)
Manager (budgetsControlled)
Programmer (project, progLanguages)
Project Manager
Dept. Manager
Strategic Manager
Triangle-arrow (△) points from sub-class up to super-class = generalization

Step 4 — Aggregation (a "has-a"/"part-of" relationship)

Aggregation means one class is made up of other classes (whole-part). It is drawn as a line with an open diamond ◇ at the "whole" end.

Invoice
◇—— has ——>
Customer
Payment
Receipt
Example: an Invoice is built from/linked to Customer, Payment and Receipt information

Step 5 — Draw the class diagram

Each class is a 3-part box: class name on top, attributes in the middle, operations at the bottom. Join classes with:

  • plain line = association ("uses"/"knows about")
  • line + open triangle at super-class = generalization
  • line + open diamond at whole-class = aggregation

Imp points to mention

  • Name all four object-identification approaches (grammatical, tangible, behavioural, scenario-based), even if you only use one.
  • Clearly separate attributes vs operations in each class box.
  • Explicitly point out which relationship is generalization (triangle, "is-a") and which is aggregation (diamond, "has-a"/"part-of").
  • Say generalization = inheritance in code; aggregation = composition of objects.
  • Keep the diagram to a reasonable number of classes (5–8) — don't overload it.

Imp QuestionCh 11 — Architectural Design
"Analyze why design conflicts might arise when designing an architecture (e.g., availability vs. security requirements)."

Every non-functional requirement pulls the architecture in a certain direction. The problem is different requirements pull in opposite directions — satisfying one makes another harder. That's a design conflict.

CharacteristicWhat the architecture should do for it
PerformanceKeep related operations close together (few, large components); minimise communication between components.
SecurityUse a layered architecture; keep critical assets in inner layers with controlled access.
SafetyKeep safety-critical features localised in a small number of sub-systems.
AvailabilityInclude redundant components and mechanisms for fault tolerance.
MaintainabilityUse fine-grained, easily replaceable components.

Why availability vs security specifically conflicts

Availability wants the system to never go down — the standard way to do that is to add redundant copies of data and components, and multiple access points, so if one fails another takes over. But security wants to minimise who/what can touch the critical data — fewer access points, tightly controlled, ideally one well-guarded place. So:

  • More redundant copies (good for availability) = more places an attacker could target = harder to secure.
  • Locking data down to one well-guarded layer (good for security) = a single point of failure = bad for availability.

Example: a banking system needs to be always available, so you'd replicate the account database across multiple servers/locations. But now you must secure every replica identically, encrypt every synchronisation channel, and manage access control consistently everywhere — the attack surface has grown even though each server on its own is simple. If you instead centralise everything into one heavily-secured server, that server becomes a single point of failure, hurting availability.

Other common conflict pairs (mention if the question is generic):

  • Performance vs Maintainability: large, tightly-coupled components run faster but are harder to change.
  • Safety vs Performance: isolating safety-critical code means more inter-component communication, which slows things down.

Imp points to mention

  • Definition line: "architectural design decisions involve trade-offs between competing quality attributes."
  • The five characteristics table (Performance, Security, Safety, Availability, Maintainability) with their strategy.
  • Explicit two-line explanation of why redundancy (availability) increases attack surface (security).
  • One concrete example system (banking / hospital / e-commerce).
  • Mention at least one more conflicting pair (Performance vs Maintainability, or Safety vs Performance).

PYQ / Sample PaperCh 11
"Discuss the fundamental questions that need to be answered by the system architects during the architectural design process."

Architectural design is creative and differs project to project, but every architect must answer the same core set of questions:

  • Is there a generic/reusable application architecture that fits? — can an existing reference architecture be reused instead of starting from scratch?
  • How will the system be distributed across processors/computers?
  • What architectural style(s) are appropriate for this system (repository, client-server, layered, pipe-and-filter, etc.)?
  • What approach will be used to structure the system? (how sub-systems are organised)
  • How will the system be decomposed into modules? (object model vs pipeline model)
  • What control strategy should be used? (centralised vs event-driven)
  • How will the architectural design be evaluated? — against what quality attributes?
  • How should the architecture be documented? — which models/notations will describe it?

These questions matter because architecture is the earliest big decision point — it sits between requirements and detailed design, and getting it wrong is expensive to undo later. Answering these questions well also gives stakeholders a shared picture to discuss and lets you analyse early whether non-functional requirements (performance, security, etc.) can even be met.

Imp points to mention

  • List all eight questions — examiners usually count how many you remember.
  • Mention architectural design sits "between specification and design" and is often done in parallel with specification.
  • Mention the three benefits of explicit architecture: stakeholder communication, system analysis, large-scale reuse.
